# 决策记录

记录每个默认值为什么是现在这样，尤其是 Jim 过往项目之间意见不一的地方。以后要改某个默认值，先看这里。

格式：决策 · 理由 · 来源 · 日期。

## 2026-11-01 · 0.1.0 初版

调研了 Jim 过往的四个产品项目（后台、移动端、商城、工具）。点名的只有开源的 greenhouse（web + 历史上的 Native Haven v2 规范），其余写作「其他项目」。

注（2026-11-06 补）：本节的「greenhouse v1 / v2」是 Greenhouse 4.0 之前的两版 web 客户端，「Haven v2」是当时的原生规范，CrudDetail 是 v2 的列表详情抽屉。4.0 起 Greenhouse 只有一个 Expo 通用客户端（web、桌面、iOS、Android 共用 `apps/client`），这些实现都已删除。下表的理由仍然成立，但不要再去 Greenhouse 里找这些出处；现行出处见「2026-11-06 · 1.1.0」。

## 2026-11-08 · 1.2.0 交互层共用，皮肤开放

起因：要能从 jim-uiux 反查到用它的项目，上游改了往下推，项目里的好做法提回来。盘点时发现 ivan 有一整套成熟的设计系统「墨」，交互规则和 jim-uiux 大体一致，但品牌、字体、图标都是自己的；greenhouse 也是这样。Jim 提出：皮肤开放给项目，jim-uiux 只维护共用的交互组件和规范。

| 决策 | 理由 | 被放弃的方案 |
| --- | --- | --- |
| 皮肤可以整套换（之前只开放几个旋钮） | 「墨」和 Haven 都是成熟的品牌，硬套黑白会丢掉品牌，结果是项目干脆不用 kit；组件只认语义名，换值不影响交互 | 只开放旋钮；每个项目 fork 一份 kit |
| jim-uiux 维护交互层、语义名和一套默认皮肤；领域组件留在项目 | 焦点、层叠、反馈这些最容易各写各错，也最值得共用；领域组件离开项目就没有意义 | 把净值图、提交图这类领域组件也收进来 |
| 底线和语义不随皮肤变：对比度、12px、44px、颜色不是唯一信号、减少动效；一个强调色，红色表示危险 | 这些是可用性和含义，不是风格。领域里红色另有含义（A 股的涨）时，项目写明报错用什么颜色 | 底线也交给项目 |
| 下游分 `registry`（装组件）和 `aligned`（按规范自己实现）两种，登记在 `consumers.json` | GitHub 的代码搜索查不全（retrace、arbor 都搜不到），名单要自己记；`aligned` 项目写 `follows`，改了规范才知道影响谁 | 用到时临时搜索 |
| 名单只点名开源项目，私有项目写进不提交的 `consumers.local.json` | 和本文开头「只点名开源的项目」一致 | 私有项目也写进公开名单 |
| 反哺门槛：两个项目要用，或一个项目验证过、明显通用；不带领域含义 | 防止把一个项目的偏好变成所有项目的默认 | 项目加了就收 |
| ivan 先按 `aligned` 登记，不急着换组件 | 它的组件手写但完整，交互规则已经一致；换组件是 ivan 自己的工作，先桥接 token，再从浮层和菜单换起 | 立刻把 ivan 迁到 registry；不登记 ivan |

## 2026-11-08 · 1.3.0 收下游的三项

起因：1.2.0 的比对脚本发现 retrace、arbor 在 kit 组件上自己加了几样。它们通用，只用语义 token，按 `downstream.md` 的门槛（一个项目验证过、明显通用）收回来。

| 决策 | 理由 | 被放弃的方案 |
| --- | --- | --- |
| `notify.prompt`：常驻、带一个动作、同一个 id 再弹会替换；`notify.loading`：返回 id，结束时收起 | 出自 retrace 的自动更新：「已下载，重启」不是错误，却要等用户处理；下载时要让人知道在进行。桌面应用都会遇到 | 用 `notify.error` 常驻；项目直接调 sonner 的 `toast()` |
| loading 图标用 kit 的 `Spinner`，Toast 的图标槽加 `relative` 和固定尺寸 | sonner 把自定义 loading 图标绝对定位到最近的定位祖先；unstyled 模式下图标槽没有定位，转圈会画在 Toast 正中、压住文字（retrace 现在就是这样） | 照搬 retrace 的写法 |
| 新增 `ContextMenu`，两种菜单都加子菜单；样式共用 `menuClass`；`MenuParts` 让一份项列表同时用于 ⋯ 菜单和右键菜单 | retrace 的项目列表右键和 ⋯ 是同一组项，自己写了 MenuKit 保证两边不走样。右键在触屏上要长按、键盘上基本用不了，所以只能是快捷方式 | ContextMenu 复制一份样式；允许操作只放在右键里 |
| 子菜单只开一层，放一组同类选项 | 多层子菜单要斜着精确移鼠标，键盘也难找；选项多了就该用 Combobox 或弹框 | 不限层数 |
| 新增 `PopoverAnchor`；点换了就传新的 `virtualRef` 对象 | arbor 在 3D 视图里改尺寸，浮层要锚到一个点。Radix 只在锚对象变了时才重新定位；而且锚对象固定、又有 PopoverTrigger 时，开发环境的 StrictMode 会让 trigger 抢回锚点，浮层跑到左上角（gallery 示例里踩到过） | 在点上叠一个隐藏按钮当触发器；手写绝对定位的浮层 |

## 2026-11-17 · 1.6.0 列表详情：遮罩与翻页

来源：另一个项目（一个工作台类应用）。它的信息流、收件箱、任务看板，都是「打开一条，看完，看下一条」。最初用的是 dock inspector（没有遮罩、点主区不关），Jim 用下来有两个问题：

- 点空白处抽屉不收，看不出什么时候算「看完了」。
- 每看一条都要关掉再点下一条。

改成「模态抽屉 + 遮罩 + 方向键翻页」后，这两个问题都没了。

- **为什么不改 dock**：dock 适合边看边在主区里操作，主区必须能点，加遮罩就违背它的本意。两种需求并存，所以分成两种用法，在 `overlays.md` 的选择表里各占一行。
- **为什么锁住打开时的顺序**：「打开即已读、未读排前」这类列表一打开就会重新排序，当前项要么挪到后面，要么从列表里掉出去，翻页就会跳或者失效。那个项目两种都实际踩过（第一种还是在写这个示例时才发现的），所以这条做进了 hook：抽屉开着时一直按打开那一刻的顺序翻。
- **为什么 ← / → 和 ↑ / ↓ 都能翻**：看板是二维的，用户会自然地按左右；列表里左右键又没有别的用处。抽屉里需要用方向键滚动长内容的情况很少，用触控板或 PageDown 滚动就行。
- **没做**：翻页时预取下一条。目前的数据量下没有必要，以后谁用到再加。

## 2026-11-24 · 1.10.2 长文目录、按需加载页面的切换
